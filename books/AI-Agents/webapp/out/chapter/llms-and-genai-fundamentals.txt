## 1. What Are Large Language Models?

### Definition

A **Large Language Model (LLM)** is an artificial intelligence system trained on massive amounts of text data to understand, generate, and manipulate human language. The "large" refers to both the size of the training data (often trillions of tokens) and the number of parameters in the model (billions to trillions).

Think of an LLM as an incredibly sophisticated autocomplete. When you type a sentence, it predicts the most likely next word (or token) based on patterns it learned during training. But unlike your phone's autocomplete, LLMs can:

- **Write** essays, code, poetry, and stories
- **Summarize** long documents into key points
- **Translate** between languages
- **Reason** through complex problems step-by-step
- **Follow instructions** given in natural language
- **Generate** structured data like JSON, SQL, or XML

### How LLMs Work

At their core, LLMs are **next-token prediction machines**. Given a sequence of tokens, they predict the probability distribution over the next possible token.

```
Input:  "The cat sat on the"
                    ↓
Model:  {"mat": 0.35, "floor": 0.25, "couch": 0.20, "roof": 0.05, ...}
                    ↓
Output: "mat" (sampled from the distribution)
```

This simple mechanism, repeated billions of times across massive datasets, produces remarkably capable language systems.

### The Training Process

Training an LLM happens in three main phases:

#### Phase 1: Pre-training (Unsupervised)

The model reads vast amounts of text from the internet, books, code repositories, and other sources. It learns to predict the next token in any sequence.

```
Objective: Given tokens [t1, t2, t3, ..., tn], predict t(n+1)

Example:
  "Artificial intelligence is the simulation of human" → "intelligence"
  "def fibonacci(n):" → "\n    if n <= 1:"
  "The capital of France is" → "Paris"
```

This teaches the model:
- Grammar and syntax
- Facts about the world
- How to reason and follow logic
- Programming patterns
- Writing styles and conventions

**Cost**: Pre-training a frontier model costs $50M-$100M+ in compute resources.

#### Phase 2: Supervised Fine-Tuning (SFT)

Human trainers create high-quality question-answer pairs to teach the model how to respond helpfully. This shapes the model from a text-predictor into an assistant.

```python
# Example training data format for SFT
{
    "messages": [
        {"role": "system", "content": "You are a helpful assistant."},
        {"role": "user", "content": "What is the capital of Japan?"},
        {"role": "assistant", "content": "The capital of Japan is Tokyo. 
        It has been the de facto capital since 1868 and is one of the 
        world's most populous metropolitan areas."}
    ]
}
```

#### Phase 3: Reinforcement Learning from Human Feedback (RLHF)

Human evaluators rank the model's responses, teaching it which answers are most helpful, harmless, and honest. The model learns to produce outputs that humans prefer.

```
Question: "How do I make a bomb?"
                    ↓
Response A: [Instructions]     → Human rates: HARMFUL (1/5)
Response B: [Refusal]          → Human rates: SAFE (5/5)
                    ↓
Model learns: Prefer refusals for dangerous requests
```

| Size Category | Parameters | Examples | Training Cost |

| Small | 1B - 7B | Phi-3, Gemma, Llama 3.2 | $10K - $500K |

## 2. The Transformer Architecture

### The Foundation of Modern AI

The **Transformer**, introduced in the landmark 2017 paper "Attention Is All You Need" by Vaswani et al., is the architecture behind virtually every modern LLM. Understanding it — even conceptually — is crucial for working with AI agents.

### High-Level Architecture

```
┌─────────────────────────────────────────┐
│              TRANSFORMER                 │
│                                          │
│  ┌────────────────────────────────────┐  │
│  │        Decoder Stack (x N)         │  │
│  │  ┌──────────────────────────────┐  │  │
│  │  │   Masked Multi-Head          │  │  │
│  │  │   Self-Attention             │  │  │
│  │  └──────────────┬───────────────┘  │  │
│  │                 │                   │  │
│  │  ┌──────────────▼───────────────┐  │  │
│  │  │   Add & Layer Normalize      │  │  │
│  │  └──────────────┬───────────────┘  │  │
│  │                 │                   │  │
│  │  ┌──────────────▼───────────────┐  │  │
│  │  │   Feed-Forward Network       │  │  │
│  │  └──────────────┬───────────────┘  │  │
│  │                 │                   │  │
│  │  ┌──────────────▼───────────────┐  │  │
│  │  │   Add & Layer Normalize      │  │  │
│  │  └──────────────┬───────────────┘  │  │
│  │                 │                   │  │
│  └─────────────────┘                   │  │
│                 │                       │
│  ┌──────────────▼───────────────┐      │
│  │   Linear + Softmax           │      │
│  │   (Output Probabilities)     │      │
│  └──────────────────────────────┘      │
└─────────────────────────────────────────┘
```

### Self-Attention: The Secret Sauce

Self-attention is what makes transformers so powerful. It allows every token in a sequence to "look at" every other token and decide how much attention to pay to each one.

#### Why Attention Matters

Consider this sentence:

> "The cat didn't cross the street because **it** was too tired."

What does "it" refer to? The cat! Humans know this instantly because we understand context. Self-attention gives models a similar ability.

#### The Q, K, V Mechanism

Every token generates three vectors:
- **Q (Query)**: "What am I looking for?"
- **K (Key)**: "What do I contain?"
- **V (Value)**: "What information do I carry?"

```python
import torch
import torch.nn.functional as F

def self_attention(Q, K, V, mask=None):
    """
    Compute scaled dot-product self-attention.
    
    Args:
        Q: Query matrix  [batch, seq_len, d_k]
        K: Key matrix    [batch, seq_len, d_k]
        V: Value matrix  [batch, seq_len, d_v]
        mask: Optional attention mask
    
    Returns:
        Attention output [batch, seq_len, d_v]
    """
    d_k = Q.size(-1)
    
    # Step 1: Compute attention scores (how much each token 
    # should attend to every other token)
    scores = torch.matmul(Q, K.transpose(-2, -1)) / (d_k ** 0.5)
    
    # Step 2: Apply mask (optional - used in decoder to prevent 
    # looking at future tokens)
    if mask is not None:
        scores = scores.masked_fill(mask == 0, float('-inf'))
    
    # Step 3: Softmax to get attention weights (probabilities 
    # that sum to 1)
    attention_weights = F.softmax(scores, dim=-1)
    
    # Step 4: Weighted sum of values
    output = torch.matmul(attention_weights, V)
    
    return output, attention_weights
```

#### Multi-Head Attention

Instead of computing attention once, the transformer computes it multiple times in parallel (multiple "heads"). Each head can focus on different aspects of the sentence:

```
Head 1: Focuses on subject-verb relationships
Head 2: Focuses on adjective-noun relationships  
Head 3: Focuses on positional/proximity patterns
Head 4: Focuses on semantic similarity
  ...
Head 12 (or more): Focuses on other patterns
```

```python
class MultiHeadAttention(torch.nn.Module):
    """Multi-Head Attention mechanism."""
    
    def __init__(self, d_model=512, num_heads=8):
        super().__init__()
        self.d_model = d_model
        self.num_heads = num_heads
        self.d_k = d_model // num_heads
        
        # Linear projections for Q, K, V and output
        self.W_q = torch.nn.Linear(d_model, d_model)
        self.W_k = torch.nn.Linear(d_model, d_model)
        self.W_v = torch.nn.Linear(d_model, d_model)
        self.W_o = torch.nn.Linear(d_model, d_model)
    
    def forward(self, query, key, value, mask=None):
        batch_size = query.size(0)
        
        # Project and reshape: [batch, seq, d_model] -> 
        # [batch, heads, seq, d_k]
        Q = self.W_q(query).view(batch_size, -1, self.num_heads, 
                                  self.d_k).transpose(1, 2)
        K = self.W_k(key).view(batch_size, -1, self.num_heads, 
                                self.d_k).transpose(1, 2)
        V = self.W_v(value).view(batch_size, -1, self.num_heads, 
                                  self.d_k).transpose(1, 2)
        
        # Compute attention for each head
        output, weights = self_attention(Q, K, V, mask)
        
        # Concatenate heads: [batch, heads, seq, d_k] -> 
        # [batch, seq, d_model]
        output = output.transpose(1, 2).contiguous().view(
            batch_size, -1, self.d_model
        )
        
        # Final linear projection
        return self.W_o(output)
```

### Positional Encoding

Unlike recurrent networks, transformers process all tokens simultaneously. But word order matters — "dog bites man" is very different from "man bites dog"! **Positional encoding** adds information about token position.

The original transformer used sinusoidal functions:

```
PE(pos, 2i)   = sin(pos / 10000^(2i/d_model))
PE(pos, 2i+1) = cos(pos / 10000^(2i/d_model))
```

Modern models use **Rotary Position Embeddings (RoPE)** or **learned position embeddings** instead, but the concept is the same: inject position information into the token representations.

### Why Transformers Beat Earlier Architectures

| Feature | RNNs/LSTMs | Transformers |
|---------|-----------|--------------|
| Parallelization | Sequential (slow) | Parallel (fast) |
| Long-range context | Poor (vanishing gradients) | Excellent (attention) |
| Training speed | Slow | Fast |
| Memory for long sequences | Limited | Scaled attention |
| Quality | Good | State-of-the-art |

## 3. Tokenization: How Text Becomes Numbers

### From Words to Tokens

LLMs don't read text — they process **tokens**, which are chunks of text converted to numbers. Understanding tokenization is critical because:

1. Token limits determine how much text a model can process
2. Token count affects API costs
3. Poor tokenization can confuse models

### Word-Level Tokenization (Simple but Limited)

```
"The quick brown fox jumps"
 ↓
["The", "quick", "brown", "fox", "jumps"]
 ↓
[464, 2159, 7586, 21831, 28403]
```

**Problem**: Every unique word needs its own token. With millions of words in English alone (plus code, technical terms, and other languages), this creates a massive vocabulary.

### Byte Pair Encoding (BPE)

BPE, used by GPT models and many others, solves this by breaking words into subword units:

```
"unhappiness"
 ↓
["un", "happy", "ness"]    # Recognizes meaningful subwords
 ↓
[345, 4912, 555]           # Three tokens instead of one
```

**How BPE works** (simplified):

1. Start with individual characters as the vocabulary
2. Count the most frequent pair of adjacent tokens
3. Merge that pair into a new token
4. Repeat until desired vocabulary size is reached

```
Corpus: "aaabdaaabac"

Iteration 1: Most common pair is "aa" → merge to "Z"
  "ZabdZabac"

Iteration 2: Most common pair is "Za" → merge to "Y"  
  "YbdYbac"

Iteration 3: Most common pair is "Yb" → merge to "X"
  "XdXac"

Final vocabulary: {a, b, c, d, X, Y, Z}
```

### Token Counts by Model

Different models tokenize differently:

| Text | GPT-4 (cl100k) | Claude | Llama 3 |
|------|----------------|--------|---------|
| "Hello, world!" | 4 tokens | 4 tokens | 5 tokens |
| "Artificial intelligence" | 3 tokens | 3 tokens | 4 tokens |
| "def fibonacci(n):" | 6 tokens | 5 tokens | 7 tokens |
| 1 page of English text | ~300 tokens | ~300 tokens | ~350 tokens |

### Token Budget Management

```python
def estimate_tokens(text: str, chars_per_token: float = 4.0) -> int:
    """Quick token estimation (roughly 4 chars per token for English)."""
    return int(len(text) / chars_per_token)

# Cost estimation for different models
def estimate_cost(
    input_tokens: int, 
    output_tokens: int,
    model: str = "gpt-4o"
) -> float:
    """Estimate API cost for a request."""
    pricing = {
        "gpt-4o": {"input": 2.50 / 1_000_000, 
                    "output": 10.00 / 1_000_000},
        "gpt-4o-mini": {"input": 0.15 / 1_000_000, 
                         "output": 0.60 / 1_000_000},
        "claude-sonnet-4-20250514": {"input": 3.00 / 1_000_000, 
                                      "output": 15.00 / 1_000_000},
        "claude-haiku-3-5-20241022": {"input": 0.80 / 1_000_000, 
                                       "output": 4.00 / 1_000_000},
    }
    
    rates = pricing.get(model, pricing["gpt-4o"])
    cost = (input_tokens * rates["input"] + 
            output_tokens * rates["output"])
    return cost

# Example: Processing a 5,000-word document
document_tokens = 6_500  # ~5000 words
response_tokens = 1_000  # expected response length

cost = estimate_cost(document_tokens, response_tokens, "gpt-4o")
print(f"Cost per request: ${cost:.4f}")
# Cost per request: $0.0263
```

### Open-Source vs. Closed Models

**Closed Models** (GPT-4, Claude, Gemini):
- ✅ Best quality and safety
- ✅ No infrastructure needed
- ✅ Always up-to-date
- ❌ API costs add up
- ❌ Data sent to provider
- ❌ Rate limits and availability

**Open-Source Models** (Llama, Mistral, Mixtral):
- ✅ Full data privacy
- ✅ No per-token costs
- ✅ Customizable and fine-tunable
- ✅ Run anywhere
- ❌ Need GPU infrastructure
- ❌ Requires ML expertise
- ❌ Generally lower quality than frontier models

## 5. Context Windows

### What Is a Context Window?

A **context window** is the maximum amount of text an LLM can process in a single request. It includes both your input (prompt) AND the model's output (response).

```
┌──────────────────────────────────────────────────┐
│                CONTEXT WINDOW                     │
│                                                   │
│  ┌─────────────────────────┐  ┌────────────────┐ │
│  │      INPUT (Prompt)     │  │   OUTPUT       │ │
│  │                         │  │   (Response)   │ │
│  │  System prompt          │  │                │ │
│  │  Conversation history   │  │  Model's       │ │
│  │  User message           │  │  generated     │ │
│  │  Documents/context      │  │  text          │ │
│  │  Examples               │  │                │ │
│  └─────────────────────────┘  └────────────────┘ │
│                                                   │
│         Total: Must fit within context limit      │
└──────────────────────────────────────────────────┘
```

### Why Context Windows Matter for Agents

AI agents typically need **large context windows** because:

1. **Conversation history**: Multi-turn conversations accumulate tokens quickly
2. **Tool results**: Retrieving documents, API responses, and data fills context
3. **System instructions**: Agent prompts with tools, rules, and examples
4. **Working memory**: Scratchpads and intermediate reasoning steps

```python
# Example: Agent context usage
agent_context = {

    "conversation_history": 3000, # Last 10 messages
    "retrieved_documents": 5000,  # RAG results
    "tool_descriptions": 1500,    # Available tools
    "user_message": 500,          # Current request
    "reserved_for_output": 2000,  # Response space
    # Total: ~12,800 tokens
}
# Well within GPT-4o's 128K limit
# But could be a problem with smaller context models
```

### Managing Context

```python
class ContextManager:
    """Manages context window usage for an AI agent."""
    
    def __init__(self, max_tokens: int = 128000):
        self.max_tokens = max_tokens
        self.reserved_output = 4096
        self.available = max_tokens - self.reserved_output
    
    def estimate_tokens(self, text: str) -> int:
        """Rough estimation: ~4 chars per token."""
        return len(text) // 4
    
    def truncate_history(
        self, messages: list, keep_recent: int = 10
    ) -> list:
        """Keep only recent messages if too many."""
        if len(messages) > keep_recent:
            # Always keep system message
            system = [m for m in messages if m["role"] == "system"]
            recent = messages[-keep_recent:]
            return system + recent
        return messages
    
    def fits_in_context(self, messages: list, 
                         extra_tokens: int = 0) -> bool:
        """Check if everything fits in context window."""
        total = sum(
            self.estimate_tokens(m["content"]) for m in messages
        ) + extra_tokens
        return total <= self.available
```

## 6. Temperature & Sampling

### The Creativity Knob

**Temperature** controls how random or deterministic the model's output is. It's one of the most important parameters you'll use.

```
Temperature Scale:

0.0        0.3        0.7        1.0        1.5+
│──────────│──────────│──────────│──────────│
Deterministic                               Random
Predictable                                 Creative
"By the book"                              "Off the wall"

Use for:            Use for:          Use for:
- Code generation   - Chatbots        - Creative writing
- Fact extraction   - Summarization   - Brainstorming
- Data processing   - General Q&A     - Poetry
```

### How Temperature Works

Temperature modifies the probability distribution before sampling:

```python
import numpy as np

def apply_temperature(logits: list[float], temperature: float) -> list[float]:
    """
    Apply temperature scaling to logits.
    Lower temperature → sharper distribution (more deterministic)
    Higher temperature → flatter distribution (more random)
    """
    # Convert logits to probabilities with temperature
    scaled = [logit / temperature for logit in logits]
    
    # Subtract max for numerical stability
    max_logit = max(scaled)
    exp_logits = [np.exp(l - max_logit) for l in scaled]
    
    # Normalize to probabilities
    total = sum(exp_logits)
    probabilities = [e / total for e in exp_logits]
    
    return probabilities

# Example: Model deciding between three options
logits = [5.0, 3.0, 1.0]  # "yes", "maybe", "no"

print("Temperature 0.1 (near-deterministic):")
probs = apply_temperature(logits, 0.1)
# → [0.9999, 0.0001, 0.0000]  → Almost always picks "yes"

print("Temperature 0.7 (balanced):")
probs = apply_temperature(logits, 0.7)
# → [0.73, 0.18, 0.09]        → Usually "yes", sometimes others

print("Temperature 1.5 (creative):")
probs = apply_temperature(logits, 1.5)
# → [0.47, 0.30, 0.23]        → More varied choices
```

### Top-p (Nucleus) Sampling

Instead of considering all possible next tokens, **top-p** sampling only considers tokens whose cumulative probability exceeds a threshold.

```
Token probabilities:
  "the"    : 0.35  ─┐
  "a"      : 0.20   │  top_p=0.9: These tokens
  "one"    : 0.15   │  are considered
  "this"   : 0.12  ─┘
  "some"   : 0.08  ─┐
  "that"   : 0.05   │  Excluded by
  "every"  : 0.03   │  top_p threshold
  "each"   : 0.02  ─┘
```

### Top-k Sampling

**Top-k** limits sampling to the k most probable tokens, regardless of their individual probabilities.

```python
def top_k_sample(logits: list[float], k: int = 50) -> str:
    """Sample from the top k most probable tokens."""
    # Sort by probability
    indexed = sorted(enumerate(logits), key=lambda x: x[1], 
                     reverse=True)
    
    # Keep only top k
    top_k_indices = [idx for idx, _ in indexed[:k]]
    top_k_logits = [logits[i] for i in top_k_indices]
    
    # Sample from remaining
    probabilities = apply_temperature(top_k_logits, temperature=1.0)
    chosen_idx = np.random.choice(top_k_indices, p=probabilities)
    
    return chosen_idx
```

### Practical Settings Guide

| Use Case | Temperature | Top-p | Top-k |
|-----------|------------|-------|-------|
| Code generation | 0.0 - 0.2 | 0.95 | - |
| Data extraction | 0.0 | 1.0 | - |
| Factual Q&A | 0.0 - 0.3 | 0.9 | - |
| General chatbot | 0.7 | 0.9 | 50 |
| Creative writing | 0.9 - 1.2 | 0.95 | 100 |
| Brainstorming | 1.0 - 1.5 | 1.0 | - |

## 7. Prompt Engineering Basics

### What Is Prompt Engineering?

**Prompt engineering** is the art and science of crafting inputs to LLMs to get desired outputs. It's the primary interface between humans and AI models, and it's essential for building effective AI agents.

### Zero-Shot Prompting

Give the model a task with no examples:

```
Classify the following text as positive, negative, or neutral:

"The product arrived on time and works as expected."

Classification:
```

```python
# Zero-shot classification
response = client.chat.completions.create(
    model="gpt-4o",
    messages=[
        {"role": "system", "content": "You are a sentiment classifier."},
        {"role": "user", "content": """Classify the following text as 
        positive, negative, or neutral:
        
        "The product arrived on time and works as expected."
        
        Classification:"""}
    ],
    temperature=0.0
)
print(response.choices[0].message.content)
# Output: "Positive"
```

### Few-Shot Prompting

Provide examples to guide the model:

```

Sentiment: Positive

Review: "The delivery was late and the package was damaged."
Sentiment: Negative

Review: "It's an okay product, nothing special."

Sentiment:
```

### Chain-of-Thought (CoT) Prompting

Ask the model to show its reasoning step by step:

```
Question: A store has 15 apples. They sell 8 and then receive 
a delivery of 12. How many apples do they have now?

Let me think step by step:
1. Start with 15 apples
2. Sell 8: 15 - 8 = 7 apples
3. Receive 12: 7 + 12 = 19 apples

Answer: 19 apples
```

```python
# Chain-of-thought for complex reasoning
response = client.chat.completions.create(
    model="gpt-4o",
    messages=[
        {"role": "system", "content": """You are a helpful math tutor.
        Always show your reasoning step by step."""},
        {"role": "user", "content": """Question: If I buy 3 shirts at 
        $25 each and pay 8% tax, how much do I owe?
        
        Think step by step:"""}
    ],
    temperature=0.0
)
# Output will walk through: 3 × $25 = $75, 
# tax = $75 × 0.08 = $6, total = $81
```

### System Prompts

System prompts set the model's behavior, role, and constraints:

```python
# Effective system prompt for an agent
system_prompt = """
You are a helpful customer support agent for TechCorp.

## Your Role
- Answer customer questions about TechCorp products
- Help troubleshoot technical issues
- Process returns and refunds according to policy

## Guidelines
- Be friendly and professional
- If you don't know the answer, say so honestly
- Never make up product features or pricing
- For billing issues, always verify customer identity first
- Escalate to human agent if the customer is frustrated

## Available Actions
- search_knowledge_base(query): Search product documentation
- check_order_status(order_id): Look up order information
- initiate_return(order_id, reason): Start a return process
- escalate_to_human(reason, priority): Transfer to human agent

Always use the appropriate action when needed.
"""
```

### Prompt Patterns

#### Pattern 1: Role + Task + Format

```
Role: You are a senior data analyst.
Task: Analyze the following sales data and identify trends.
Format: Present your findings as bullet points, 
        followed by a recommendation.
```

#### Pattern 2: Constraints + Output

```
Write a product description for running shoes.
Constraints:
- Max 50 words
- Include: comfort, durability, price ($89)
- Tone: enthusiastic but professional
- No superlatives ("best", "greatest")
```

#### Pattern 3: Delimiter Separation

```
Analyze the following customer feedback:

---FEEDBACK_START---
The interface is confusing and I keep getting errors 
when trying to export my data. Very frustrating experience.
---FEEDBACK_END---

Provide:
1. Sentiment (positive/negative/neutral)
2. Key issues mentioned
3. Suggested improvement for each issue
```

### Common Prompt Engineering Mistakes

| Mistake | Example | Fix |
|---------|---------|-----|
| Too vague | "Tell me about dogs" | "Compare Golden Retrievers vs. Labradors as family pets" |
| No format specified | "Analyze this data" | "Analyze this data as a markdown table with columns: Metric, Value, Trend" |
| Ambiguous constraints | "Keep it short" | "Keep the response under 100 words" |
| No examples | Complex classification | Provide 2-3 labeled examples |
| Missing context | "Is this good?" | "Given our KPI targets (revenue > $1M, churn < 5%), is this quarter's performance good?" |

### Streaming Responses

```python
def stream_completion(prompt: str, model: str = "gpt-4o"):
    """Stream the response token by token for better UX."""
    stream = client.chat.completions.create(
        model=model,
        messages=[
            {"role": "user", "content": prompt}
        ],
        temperature=0.7,
        stream=True
    )
    
    print("Response: ", end="", flush=True)
    for chunk in stream:
        if chunk.choices[0].delta.content:
            print(chunk.choices[0].delta.content, 
                  end="", flush=True)
    print()  # New line at the end

# Usage
stream_completion("Write a haiku about programming.")
```

### Error Handling

```python
import time
from openai import (
    OpenAI, 
    APIError, 
    RateLimitError, 
    APITimeoutError
)

def robust_completion(
    messages: list[dict],
    model: str = "gpt-4o",
    max_retries: int = 3
) -> str:
    """Completion with retry logic and error handling."""
    
    for attempt in range(max_retries):
        try:
            response = client.chat.completions.create(
                model=model,
                messages=messages,
                temperature=0.7,
                max_tokens=1000,
                timeout=30  # 30 second timeout
            )
            return response.choices[0].message.content
            
        except RateLimitError:
            wait_time = 2 ** attempt  # Exponential backoff
            print(f"Rate limited. Waiting {wait_time}s...")
            time.sleep(wait_time)
            
        except APITimeoutError:
            print(f"Timeout on attempt {attempt + 1}. Retrying...")
            
        except APIError as e:
            print(f"API error: {e}")
            raise
    
    raise Exception(f"Failed after {max_retries} retries")
```

## 9. Key Takeaways

1. **LLMs are next-token prediction machines** trained on massive text datasets. They learn patterns, facts, and reasoning from their training data.

2. **Transformers use self-attention** to process all tokens in parallel, allowing them to capture long-range dependencies in text far better than previous architectures.

3. **Tokenization converts text to numbers** using techniques like BPE. Understanding token counts is crucial for managing costs and context windows.

4. **The GenAI landscape offers many options**: closed models (GPT-4, Claude, Gemini) for best quality, open-source models (Llama, Mistral) for privacy and control.

5. **Context windows determine capacity**: Larger windows (128K+) enable complex agents with rich conversation history and tool results.

6. **Temperature and sampling control output**: Lower temperature for deterministic tasks, higher for creative ones.

7. **Prompt engineering is an essential skill**: Zero-shot, few-shot, chain-of-thought, and system prompts are your primary tools for getting desired outputs.

8. **Error handling and streaming** are practical necessities when building production applications with LLM APIs.
